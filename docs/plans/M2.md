## Goal

Core turns the tokenized events M1 stores into a map: which fields across systems identify the
same record. The profiler sketches every identifier field, the linker proposes exact, bridge and
composite key links with their evidence, a reviewer accepts or rejects them in the first screen
of the console, accepted links form entity families with names, and the eval harness scores all
of it against simulator truth. The same engine runs over an offline bundle, which is how the
go/no-go gate on the first design partner's data is run.

## How the engine runs

1. `ingest-api` and `load-bundle` keep writing `events` and `event_identifiers` (M1).
2. `carto-core worker` leases jobs from the PostgreSQL `jobs` table (`SELECT ... FOR UPDATE SKIP
   LOCKED`, spec 5.3). Two jobs exist in M2: `profile` (every 5 minutes by ingest watermark;
   nightly full window rebuild) and `link` (after each profile pass over new sketches; a full
   candidate pass nightly).
3. The profiler reads new identifier rows from the event store, updates one sketch set per
   `(field, form, day)` and writes `fields` and `field_sketches`. The 7-day window is the merge
   of the last seven daily sketches, so the nightly rebuild and the 5-minute update are the same
   code path.
4. The linker builds the LSH index from the window sketches of fields that pass `q`, queries
   candidates, adds bridge pairs, verifies every candidate with one join query per pair in the
   event store, scores, filters, assigns direction and role, and upserts `key_links` with the
   evidence. Composite matching runs for system pairs with temporal adjacency and no exact link
   above 0.5.
5. The API serves the queue; decisions go to `key_links`, `audit_log` and the family rebuild.
6. `carto-core discover --bundle <dir> --out <dir>` runs steps 3 and 4 once over a loaded
   bundle and writes the eval prediction files (`links.json`, `entities.json`) and the gate
   report input. The eval driver and the partner gate both use it.

The event store is a Protocol (`carto_core.store.EventStore`) with the handful of typed queries
the engine needs: identifier rows after a watermark, token join between two `(field, form)`
ends with first-seen times and fanout, co-occurring identifier fields per template, and token
samples by `(field, form, day)`. ClickHouse is the only implementation (founder decision 3). Pure
engine logic (scoring, filters, families, composite weights) is unit-tested against an in-memory
fake of the Protocol; every query of the ClickHouse implementation is covered by integration
tests in a container, including a duplicated batch, so each query is proven to deduplicate by
`event_id` under the `ReplacingMergeTree` tables of ADR 0034. Local eval runs need Docker.

## Decisions proposed with this plan

Each becomes an ADR (0046 onward; 0033 to 0045 belong to the M1 review fixes) when building
starts, unless the founder objects.

1. **Event store behind a Protocol with one implementation, ClickHouse.** The Protocol exists
   so the engine's logic is tested without a database (an in-memory fake) and so the queries
   are listed in one place; there is no second SQL dialect. A SQLite implementation for
   machines without Docker was proposed and declined by the founder on 2026-10-12, who fixes
   Docker on the development machine instead.
2. **Daily sketches.** `field_sketches` is keyed by `(field_id, form, day)`; the window is a
   merge. MinHash and HyperLogLog merge natively; the bottom-k sample is the 2,048 smallest
   64-bit hashes of the tokens and merges by taking the smallest again, which also gives an
   exact containment estimate for verification without a database round trip.
3. **Verification is SQL in the store.** One join per candidate pair returns `n_match`, the lag
   distribution, fanout both ways and the top-10 concentration; `n_a` and `n_b` come from the
   sketches. `domain_size` for the chance ratio comes from the dominant shape as spec 9.3 says.
   Candidates are capped per run (default 5,000 pairs, highest estimated containment first) so a
   50-system install finishes a full pass inside the spec 17 budget of 30 minutes.
4. **Scoring weights are versioned configuration.** v1 ships hand-set weights in
   `linker/weights.py`. The eval harness gains `carto-eval fit-weights`, which fits a logistic
   regression on scenario A and C truth with scikit-learn and writes a weights file; core never
   imports scikit-learn. The eval report shows the metrics for the shipped weights.
5. **Eval acceptance policy.** The product keeps auto-accept off. In an eval run, proposed
   transaction and bridge links at or above the proposal threshold (score 0.5) count as accepted
   for family building, so entity purity measures the engine, not a simulated reviewer. The
   report states this.
6. **Engine fields map to truth fields by source and path.** The engine knows a field as
   `system_id/template_id/path`; the truth knows `(system_id, source_id, field)` where `field`
   is the name in the data (`merchantRef`, `order_ref`, `cart_id`). The driver maps through
   the source that carries the template and the flattened path, and lists every engine field
   that matched no truth field and the reverse, so a naming mismatch is visible in the report,
   never silently scored as a miss.
7. **Review items in M2 show counts, shapes, lag and the sentence, not example transactions.**
   Transactions and reveal exist from M3; the queue item gains them then (spec 4.3 item 1).
8. **The edge reports its inventory to core; core shows it read-only.** On start and on every
   change of its sources file, the edge sends `POST /internal/inventory` (mutual TLS, role
   `edge-gateway`): systems with names and descriptions, sources with type, configuration
   without secrets (`secret_ref` name only), schedule, backfill window and the field policy
   pins; heartbeats keep carrying health, cursor age, lag and the last error, plus the last
   read-only test result. Core upserts `systems`, `sources` and `fields.policy` and the console
   shows Systems, Setup › Sources and Setup › Field policies as read-only screens in M2, so a
   user sees what is connected and how healthy it is from the first login. Writing
   configuration from the console to the edge (the control plane) stays deferred; it is a
   new path across the trust boundary and is decided at M6 planning. Founder decision 2:
   "pull in more info for users as soon as we can".
9. **Audit log lands in M2.** Invariant 6 covers review decisions and entity naming, so the
   append-only hash-chained `audit_log` table with INSERT-only grants, the trigger that rejects
   UPDATE and DELETE, and `carto-ctl audit verify` for core arrive with the first mutating
   endpoint. External anchoring stays in M6 (spec 21).
10. **One origin.** The web app is static files served by nginx behind the customer's ingress
    with the API on the same origin under `/api/v1`, so the `__Host-` session cookie, CSRF
    header and the `default-src 'self'` CSP hold without exceptions. Compose gains `api`,
    `worker` and `web` services.
11. **Staleness is a status in M2, an alert in M4.** The linker marks an accepted link `stale`
    when its match rate drops more than 50% against the 7-day baseline; the schema drift signal
    (spec 10.2) is built with the detector.
12. **Providers are adapters behind one `Provider` Protocol, registered by name.** An adapter
    is one module with `complete(task_prompt, payload_json, output_schema) -> str` and a
    settings model (endpoint, model, credential `secret_ref`), nothing else; the gateway owns
    fencing, schema validation, the egress allowlist, audit and retries, so an adapter cannot
    weaken them. A conformance test module runs every registered adapter against a recorded
    exchange. M2 ships the Anthropic Messages API adapter, an OpenAI-compatible chat
    completions adapter (which covers most self-hosted and gateway deployments) and the fake
    used by tests and the injection corpus; Bedrock and Vertex are one module each when a
    partner asks. `httpx` only, no vendor SDK. Founder decision 4.
13. **Every 9.x threshold is a setting** (`LinkerSettings`, `ProfilerSettings`) with the spec
    default, so eval tuning never edits code.

### B. Profiler (`core/carto_core/profiler/`)

- Incremental pass by ingest watermark: identifier rows grouped by `(field_ref, form, day)`;
  shape histogram and length statistics; null rate from template event counts.
- Sketches with `datasketch` (MinHash 128, HyperLogLog, LSH Ensemble) and the bottom-k sample.
- `q(field)` exactly as spec 9.1; the `fields` rows carry `class`, `policy`, `distinct_estimate`,
  `null_rate`, `shapes_json`, `first_seen`, `last_seen`.
- Property tests: merging daily sketches equals sketching the union; containment estimates
  within tolerance of exact containment on generated token sets; `q` is monotonic in distinct
  ratio and top-shape share.

### C. Linker: exact, bridges, families, naming (`core/carto_core/linker/`)

- Candidate generation per spec 9.2 with the per-run cap; bridge candidates from
  `cooccurring_fields` with the functional-dependency consistency of spec 9.4.
- Verification join per pair; `PairFeatures`; logistic score with the hand-set weights; hard
  filters (`concentration > 0.5`, `chance_ratio > 0.3`, `n_match < 20`); direction and role
  rules with the spec thresholds.
- Review state machine (`proposed`, `accepted`, `rejected`, `auto_accepted`, `stale`) with the
  re-proposal rule and versioned decisions.
- Families as connected components over accepted transaction links and bridges; heuristic
  naming from the spec dictionary over field paths, template text and shapes; LLM suggestion
  through package G when enabled.
- Property tests: the score is monotonic in containment and antitonic in concentration and
  chance ratio; direction flips when the ends swap; a family never contains a rejected pair.

### D. Composite links (`core/carto_core/linker/composite.py`)

- Temporal adjacency: for system pairs without an exact link above 0.5, hourly volume
  cross-correlation and lag consistency over the window.
- Blocking on shared `date` or `amount` tokens within the window (default 3 business days using
  the tenant calendar, Monday to Friday until M4 adds calendars).
- Components: `date`, `amount`, `phonetic.k`, low-cardinality attributes, identifier forms with
  partial overlap; Fellegi-Sunter with `m` from EM and `u` from random pair sampling; threshold
  chosen for precision 0.9 on the simulator and stored with the rule.
- `composite_rules` rows and per-pair matches kept for M3 assembly; never auto-accepted.

### E. API, authentication, authorization, audit (`core/carto_core/api/`)

- FastAPI app `carto-core api`: the M2 endpoints, cursor pagination, RFC 7807 errors, request
  ids, `ETag` and `If-Match` on links and entities, the spec 14.7 headers and rate limits.
  Read-only `GET /systems`, `GET /sources`, `GET /sources/{id}`, `GET /sources/{id}/health`
  and `GET /fields` serve the inventory of decision 8; `POST /internal/inventory` receives it.
- Authentication: OIDC authorization code flow with PKCE through Authlib (founder decision 1),
  roles from the ID token groups claim mapped by `role_bindings`; Dex (Apache-2.0) as the
  identity provider in the Compose `dev` profile and CI with static test users for each role.
  Server-side sessions with the `__Host-carto_session` cookie flags and timeouts of spec 14.1;
  CSRF synchronizer token; step-up (`max_age`) wired but not required by any M2 action.
- Authorization: `require(permission)` only; the matrix test calls every endpoint as every role
  and compares with the spec 14.2 table; `reveal` is not granted to anyone in M2.
- Audit on every mutation; `GET /audit` for admin and auditor.

### G. LLM gateway (`core/carto_core/llm_gateway/`)

- Task schemas for field labels and entity names; payload builder reads metadata tables only

## Questions for the founder

Answered 1 to 4 on 2026-10-12 (recorded after the list); 5 to 7 open.

1. **How do people log in to the first screen?** The spec's main path is single sign-on
   (OIDC) and M6 says "SSO and RBAC complete". Two ways to reach M2's review screen:
   (a) build OIDC now with Authlib and run a small open-source identity provider (Dex) in the
   Compose `dev` profile and CI, so the roles, sessions and the authorization matrix test exist
   from the first endpoint, and M6 only adds scoped bindings and the break-glass admin; or
   (b) build the spec's break-glass local admin (password plus one-time code) now and OIDC in
   M6. Recommendation: (a). It is more work in M2 but means the partner pilot never runs on a
   local password, and nothing has to be rebuilt in M6.
2. **Where does the list of systems and sources come from?** The M1 edge reads its sources
   from a file the admin writes. Core can learn systems and sources from what the edge sends
   (decision 8) and show them read-only. The spec's Setup › Sources screen, where an admin adds
   a connector in the console and presses Test, needs core to write connector configuration to
   the edge. That is a new control path across the trust boundary and is not assigned to a
   milestone in the spec. Recommendation: read-only in M2, and decide the control path at M6
   planning with the install guide.
3. **May the engine have a second, small event store for tests?** The engine's joins run in
   ClickHouse. This laptop cannot run containers (Docker Desktop and WSL are stuck), so without
   a local store the eval loop only runs in CI, which makes tuning slow. The plan proposes one
   query interface with a ClickHouse implementation and a SQLite implementation that is proven
   equal by a shared test suite. The cost is two SQL dialects for about six queries.
   Alternative: fix Docker on the laptop and keep one implementation. Recommendation: the
   interface, because it also makes `carto-core discover` runnable anywhere for the gate.
4. **LLM providers in M2.** The gateway is off by default. The plan builds the Anthropic
