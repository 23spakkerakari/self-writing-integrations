## Goal

Core follows the accepted links through the events. Every event that carries an accepted key
lands in exactly one transaction, a nightly file with thousands of records becomes one batch
linked to its transactions instead of one giant transaction, and the transactions feed a flow
graph with hop statistics and clock skew estimates. A person types any system's identifier into
search, core asks the edge for its tokens, and the trace view shows the whole path as a
timeline. A person with the reveal grant and a fresh login sees the values behind the tokens,
fetched from the edge and never stored in core. The map screen shows the systems and hops with
volume and latency, and the eval harness scores assembly and batch detection against simulator
truth.

## How the engine runs

1. `ingest-api` and `load-bundle` keep writing `events` and `event_identifiers` (M1), the
   profiler and linker keep the map (M2).
2. The worker gains two job kinds. `assemble` runs every 30 s by the `stored_at` watermark of
   `event_identifiers` (ADR 0046); `graph` runs after every assemble pass for the hop rollup
   and nightly for terminal nodes, flow variants and clock skew. `payload['full']` on
   `assemble` reassembles the window from scratch into new `txn_events` versions (after a link
   rejection, a new batch key, or by hand with `carto-core reassemble`).
3. The assembler asks the store for the events stored since the watermark together with their
   identifier tokens restricted to the **key ends**: the `(field_ref, form)` ends of accepted
   or auto-accepted exact and bridge links with the transaction role, plus the explicit event
   pairs of accepted composite links (`composite_matches`, persisted by the link pass from
   M3 on; M2 kept them in memory). Batch keys are excluded from the merge keys.
4. For each micro-batch it resolves the keys against `txn_token_index` in one PostgreSQL round
   trip (`token = ANY($1)`), runs union-find in memory over the batch, applies the hub rule
   and the guardrails, then writes in one PostgreSQL transaction: new and updated
   `transactions`, index upserts, `txn_merges`, `batch_keys`, `batches`, `batch_txns`, the
   `ambiguous_merges` counter on the responsible link, and the watermark. `txn_events` rows
   (new versions for moved events) and `hop_transitions` rows go to ClickHouse afterwards;
   a crash between the two is repaired by the next pass, which re-reads from the stored
   watermark and writes idempotent rows (same `(txn_id, event_id)` key, higher version).
5. The graph pass reads `hop_stats_hourly` over the window into the `hops` rollup, computes
   `p_next` and terminal nodes from `transactions` and `txn_events`, the top 10 flow variants
   per entity, and the per-system clock offsets from the accepted links' lag evidence.
6. The API serves traces, batches and the graph from PostgreSQL and ClickHouse; search and
   reveal go to the edge over mutual TLS with core's `api` role certificate (ADR 0031) and an
   Ed25519-signed assertion (M1 plan decision 13, `carto_common.crypto`).
7. `carto-core discover` runs profile, link, assemble and graph once over a loaded bundle and
   writes the prediction files; search is not available over a bundle (no edge to tokenize),
   traces are reached from the map, the review items and the batch list.

The store Protocol (`carto_core.store.EventStore`) gains the queries the assembler and the
graph need, each implemented in ClickHouse and in the in-memory fake and covered by the
contract suite: events since a watermark with their key tokens, the events of a transaction,
the events that carry a token, hop transition inserts, hourly hop stats over a window, and the
terminal-node counts. The index, the transactions and the batches live in PostgreSQL behind an
`AssemblyIndex` Protocol with a PostgreSQL implementation and an in-memory one, so the pure
logic (union-find, hub rule, guardrails, status, ordering) is unit-tested without a database
and the eval runs in memory as in M2.

## Decisions proposed with this plan

Each becomes an ADR (0060 onward) when code starts.

1. **Merge keys are the ends of accepted transaction links plus composite event pairs.** An
   event's keys are its tokens in the `(field_ref, form)` ends of key links whose status is
   `accepted` or `auto_accepted`, whose type is `exact` or `bridge` and whose role is
   `transaction`. Association links never merge (spec 9.3). A composite link has no shared
   token, so the link pass persists the matched event pairs it already computes
   (`composite_matches`: link id, the two event ids, the posterior, matched at) and the
   assembler treats each pair as a union of the two events' transactions. Tokens of different
   key versions never compare equal, which is how "links per key version" (spec 8.4) holds
   without code.
2. **The index is PostgreSQL, the micro-batch is resolved in memory.** `txn_token_index` is
   keyed `(tenant_id, token)`; one `SELECT ... WHERE token = ANY($1)` per micro-batch, union-find
   over the batch, one write transaction with batched upserts. The job lease is the lock: one
   assemble pass per tenant at a time. Merges go into the oldest transaction (smallest ULID,
   `carto_common.ids`), so `txn_events` rows are only ever moved from a merged-away
   transaction into a survivor; a trace read is `txn_id = ?` and never sees a stale row, and the
   membership export takes `argMax(txn_id, version)` per event. A merged-away id stays in
   `transactions` with `merged_into` set and answers 303.
3. **Hubs are bounded, not undone.** Spec 9.7 counts distinct transactions per token per day.
   The index keeps that count per token and day (`txn_token_fanout`): the number of distinct
   transactions the token has been seen with before merging through it. Ends of batch-role
   links (spec 9.3) start as batch keys and never merge. A transaction-role token whose daily
   count passes `fanout_threshold` (50) becomes a batch key: it leaves the merge index, a
   `batches` row is created, and the transactions that carried it are linked through
   `batch_txns`. Merges the token caused before the threshold stay (at most 50 transactions,
   far under the 10,000 guardrail); a full reassembly repairs them. Union-find has no split, and
   deferring every merge until a token's day is complete would cost the 30 s latency the spec
   wants for traces.
4. **Hop statistics are kept by the store.** ClickHouse holds `hop_transitions` (one row per
   consecutive node pair: hop, hour, latency, error flag; TTL 30 days like events) and a
   materialized view into `hop_stats_hourly` (AggregatingMergeTree with `count`, `countIf`
   error and a `quantilesDD` DDSketch state; TTL 13 months). ClickHouse 23.11 and later ship
   `quantileDD`, so there is no Python DDSketch dependency; the in-memory store computes exact
   quantiles. The PostgreSQL `hops` row is the rollup over the 14-day window (support, `p_next`,
   p50, p95, p99) that the API and the detector (M4) read. Transitions are appended when a
   transaction gains a new consecutive pair; a merge that interleaves events is not retracted
   from the hourly statistics (they are statistics, and the nightly rollup reads the ordered
   transactions, not the stream).
5. **Grouping templates into an event type is a view-time mapping.** A node is
   `system_id/template_id`; `templates.event_type_label` (already a column) names the group.
   `PATCH /nodes/{id}` sets a display name and an event type; the map, the traces and the
   `hops` rollup aggregate template-level hops by event type when one is set. No `txn_events`
   or `hop_stats_hourly` row is rewritten by a naming decision. `nodes` rows hold the display
   name and `is_terminal`; `PATCH /nodes/{id}` is audited (invariant 6).
6. **Clock offsets come from the link evidence.** For every accepted directed link whose
   `lag_iqr` is under 10 s and whose `lag_median` is negative, the later system is behind the
   earlier one by that median. Offsets are solved per system relative to the system with the
   most such links (offset zero), by the median of the negative lags on the walk; stored as
   `systems.clock_offset_ms` and `clock_offset_estimated_at`; used in the assembler's ordering
   key (`observed_at + offset`) and nowhere else; the map and the timeline warn when an offset
   exceeds 30 s. Scenario A's Warehouse is +90 s in truth; the eval reports the estimate as a
   measurement, not a gate, because the Warehouse link's lag is dominated by the clerks' hours.
7. **Core reaches one edge.** `ApiSettings.edge` holds the edge-gateway base URL, the CA file
   and core's client certificate and key (role `api`, from `carto-ctl pki init`). Absent, search
   and reveal answer 503 `search_unavailable` / `reveal_unavailable` and the console says the
   install has no edge. Several edges per core are an M6 question with the control plane.
8. **Search is audited at the edge, counted in core.** The edge already writes one audit row
   per tokenize call with the subject (M1). Core applies the spec 14.7 limits (`search_per_user`
   60 per minute, `search_per_address` 120 per minute, settings) and keeps a per-user counter
   that the M4 self-alert reads (threat 3). Core does not write an audit row per search; the
   audit log is for actions that change something or reveal something (spec 14.9, invariant 6).
9. **Step-up is the session's own authentication time.** `Principal.authenticated_at` (M2)
   holds the identity provider's `auth_time` or, when the provider sends none, the callback
   time. `POST /reveal` requires it within `api.step_up_max_age` (15 minutes) or answers 403
   `step_up_required` with `GET /auth/login?max_age=0&return_to=` which runs the code flow with
   `max_age=0` and `prompt=login` and replaces the session's authentication time. Dex does not
   honor `max_age` but has no persistent login for its password connector, so the Compose test
   still re-enters the password; the unit tests use the fake provider.
10. **The reveal grant is a role binding flag.** `role_bindings` gains `reveal_granted`
    (boolean, default false); `Principal.reveal_granted` is true when any of the user's bindings
    grants it. In M3 it is set by `api.bootstrap_group_roles` entries with `reveal: true` and by
    `carto-core grant-reveal <group>` (audited, admin only); the Admin screen edits it in M6.
    The auditor role can never carry it (the matrix test asserts it).
11. **Reveal is one audit row, values pass through once.** Core forwards the edge's values to
    the client in the response body and holds them in no log, cache, session or database. The
    audit row carries actor, purpose, the transaction or link the values belong to, the token
    count and the request id. The console shows revealed values in the distinct style for 60 s
    and keeps them in component state only.
12. **Transaction status in M3 is `in_progress`, `completed` or `errored`.** `completed` when
    the current node is terminal; `errored` when the last event's severity is an error;
    `stalled` is set by the detector in M4. A transaction's entity is the family of its first
    key; `entities.max_span_days` (default 14) is editable through `PATCH /entities/{id}`.
13. **Every 9.7 and 9.8 number is a setting** (`AssemblerSettings`, `GraphSettings`), as M2
    did for 9.1 to 9.6 (ADR 0055): micro-batch interval, fanout threshold, max events, default
    max span, expiry, terminal share, variants count, tight-lag IQR, skew warning.
14. **Eval policy carries over.** Links the M2 policy counts as accepted (ADR 0049 decision 5),
    plus composite links at their stored threshold, are the key ends of an eval run. The
    membership file maps engine event ids to transactions; the driver turns them into locator
    keys (ADR 0024) for the pairwise F1 of `carto_eval.metrics`, which already exists, as do
    `batch_key_precision_recall`, `PredictedBatch` and `MembershipRecord`.
15. **Load tests live in the eval package and run on the reference node.** `make load` drives
    the existing gateway benchmark (ADR 0028) at 2,000 events/s with the assembler running and
    a search load against the API; the spec names k6 for the API load. k6 is AGPL-3.0, so it
    runs as a container in CI and on the reference node and is never shipped or imported
    (question 5).

## Work packages

### A. Schema, migrations, store queries, index, jobs, settings (wave 0)

- Migrations 0005 (PostgreSQL) and 0009, 0010 (ClickHouse) with the grants: `carto_worker`
  writes the assembly tables, `carto_app` reads them; `txn_events` and `hop_transitions` are
  written by the worker's ClickHouse user only.
- The store queries above in `ClickHouseStore` and `InMemoryEventStore`; the contract suite
  covers each, including a batch loaded twice and a moved event (two `txn_events` versions).
- `AssemblyIndex` with both implementations and a shared contract suite; the PostgreSQL one
  uses `INSERT ... ON CONFLICT` batches and `= ANY` lookups and is covered by the integration
  job.
- Job kinds, worker wiring, settings sections, the schema views and the committed JSON Schema.

### B. Assembler (`core/carto_core/assembler/`)

- `keys.py`: key ends from the accepted links (`LinkRepository`) and the composite matches;
  `union_find.py`: pure, with the merge-into-oldest rule and the refusal counters;
  `batches.py`: batch-role ends, the daily fanout rule, batch rows and links; `pass_.py` (the
  `AssemblePass` the worker loads): watermark, micro-batch, write order, expiry, status,
  ordering with clock offsets, late events, the `full` reassembly.
- Property tests (spec 18.1): union-find never loses or duplicates an event; final membership
  is independent of event order when no guardrail fires, and under the guardrails the refused
  merges are the same set in any order; a batch key never merges; expiry removes exactly the
  index entries older than the span; a late event joins the transaction its key points at and
  the status is re-evaluated; `full` reassembly equals the incremental result on the same
  data.
- Coverage at least 85% on `core/carto_core/assembler`.

### C. Graph (`core/carto_core/graph/`)

- `transitions.py`: consecutive pairs of an ordered transaction, new pairs after a merge;
  `rollup.py`: `hops` from the hourly rows, `p_next`, terminal nodes, flow variants;
  `skew.py`: offsets from the link evidence; `GraphPass` for the worker.
- Property tests: hourly sums equal the transition count; `p_next` of a node's successors sums
  to at most one; a node that is always last is terminal and a node that is never last is not;
  offsets are zero when every lag is positive and recover a planted offset within 5 s.

### D. Signer, edge client, search and reveal (`core/carto_core/signer.py`, `edge_client.py`, `api/routes_traces.py`, `api/routes_reveal.py`)

- `carto-ctl key init` writes the Ed25519 signing key (wrapped by the local KMS of ADR 0025 in
  Compose; the cloud wrappers are M6) and the public key file for the edge; `carto-ctl pki
  init` already issues the `api` role certificate (ADR 0031).
- `EdgeClient`: `httpx` over mutual TLS with the pinned CA, 5 s timeout, no redirects, the
  assertion in the body as the edge expects (`carto_edge.reveal.TokenizeRequest`,
  `RevealRequest`), typed errors mapped to 502 (edge refused or unreachable, no detail from
  the edge body reaches the client), 503 when unconfigured.
- Search: query 1 to 256 characters after NFKC and trim; the edge returns tokens for every
  form; the store's `events_with_token` over the retention window; transactions through
  `txn_events`, batches through `batch_keys`; the result says which forms matched (`raw`,
  `digits.0`) so the UI can explain the hit; rate limits per user and per address; the
  per-user counter for M4.
- Reveal: the grant, step-up, the cap, the audit row, the pass-through response with
  `Cache-Control: no-store`; the logging processor test proves values never reach a log line.

### E. API: traces, batches, graph, nodes, review examples (`core/carto_core/api/`)

## Questions for the founder

1. **Hubs are bounded, not undone (decision 3).** A token that turns out to be a batch key
   after joining up to 50 transactions leaves those merges in place until a full reassembly.
   The alternative is to defer every merge through a token until its day is complete, which
   costs the 30 s trace latency. Recommendation: bounded, with the nightly full reassembly of
   the open window on by default (`assembler.nightly_rebuild`).
2. **Reveal in the pilot.** Decision 10 seeds the grant from configuration and a CLI until the
   Admin screen (M6). Should the first partner pilot run with reveal enabled for anyone, or
   with the grant empty so their security review sees the path exists but is closed?
   Recommendation: empty by default; the install guide shows how to grant.
3. **One edge per core (decision 7).** Fine for both partners' pilots? Several edges (or an
   edge per site) would need a registry and per-edge routing of tokenize and reveal, which
   belongs with the control plane question at M6 planning.
4. **Composite matching beside strong exact links** (ADR 0058 item 5, carried from M2): run
   composite matching for every adjacent system pair, with the exact link's matches excluded
   from the blocks, so scenario C's C08 is found behind C06? It costs one composite run per
   pair and some precision risk. Recommendation: yes, behind a setting defaulting to on, with
   the precision gate of 0.85 watched in the eval.
5. **k6 licence.** k6 is AGPL-3.0; it would run only as a container in CI and on the reference
   node. Acceptable as a tool, or use Locust (MIT, Python) for the search load instead?
   Recommendation: k6 as the spec names it, recorded with the licence note in the ADR.
6. **Batch truth on scenario C.** People ops plants no batches; the batch targets are shown on
   A only. Should scenario C gain the SKU spreadsheet export as a batch (one export file, many
   SKU rows) so both scenarios exercise the rule? Recommendation: yes, a small change in
   package H of M2's simulator work, done in wave 0.
7. **Scoped business viewers stay M6.** M3 reads (traces, graph, search) are unscoped for every
   role with `view`, as M2's reads are. Agreed, or does a partner need per-entity scoping for
   the trace screen before M6?
8. **Target-volume load run.** Spec 17's search target is over 30 days and 200M events, beyond
   the laptop. The plan has CI assert the query shape at one day and the founder run `make
   load` on the reference node before sign-off, as M1's throughput run was done. Agreed?
