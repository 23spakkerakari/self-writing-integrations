# M0: Foundations

Status: in progress (started 2026-10-06). Spec: `docs/SPEC.md` Section 21, "M0: Foundations".

## Goal

A repository that later milestones can build on without rework: the Section 20 layout as a `uv`
workspace, CI that runs lint, types, tests and every security scanner the spec names, the
canonical event schema as the edge-to-core contract, simulator scenario A with ground truth, and
an eval harness that can already score engine output against that ground truth.

## Package contracts fixed in M0

- **Canonical event (`carto_schema.event.CanonicalEvent`)** follows spec Section 7.1 exactly:
  `schema_version` is the string `"1"`, `event_id` is a ULID, `kind`, `observed_at_quality` and
  `actor.kind` are enums, at most 64 identifiers per event, attribute values at most 256
  characters, tokens match `t<key_version>.<22 base64url chars>`, timestamps are UTC with
  millisecond precision. Unknown keys are rejected. `template_text` is free text by construction;
  the edge is responsible for sending constants only.
- **Form names (`carto_schema.forms`)**: `raw`, `norm`, `alnum`, `digits.<k>`, `date`, `amount`,
  `phonetic.<k>` with `k` from 0 to 2 for digits and 0 to 7 for phonetic; domain mapping
  `id`, `date`, `amt`, `ph` per Section 8.4.
- **Edge-to-core envelope (`carto_schema.ingest`)**: `IngestBatch` (up to 5,000 events) and
  `SourceHeartbeat` for `POST /internal/ingest` and `POST /internal/heartbeat` (Section 12).
- **Ground truth (`carto_simulator.ground_truth`)**: see ADR 0006. Every emitted record has a
  locator key `<source_id>:<locator>`; the eval harness joins engine output on that key via a
  locator map that the edge emits in eval mode (M1).
- **Eval predictions (`carto_eval.predictions`)**: the shape of engine output the harness scores:
  links, entities, transaction membership, batches, alerts, manual hops, likely causes. Engine
  milestones (M2 to M5) write this shape; M0 scores an empty prediction and the ground truth
  itself.

## Scenario A as generated (Section 19)

Five systems, seven sources. Local time is America/New_York; log timestamps are UTC except the
warehouse database and export log, which use naive local time to exercise timezone handling.

| System | Source | Format | Identifiers |
| --- | --- | --- | --- |
| Webstore | `src_webstore_log` | NDJSON app log, one file per day | `cart_id` (`c-88213`) |
| Order system | `src_orders_log` | logfmt, one file per day | `order_id` (`4471`), bridges to `cart_id` and `merchant_ref` |
| Payments | `src_payments_xml` | one XML document per line, one file per day | `merchant_ref` (`X9-0442`) |
| Warehouse | `src_wms_db` | PostgreSQL table `purchase_orders` as SQL seed plus CSV export | `po_num` (`88-210`), `order_ref` (`SO-0004471`) |
| Warehouse | `src_wms_export_log` | unstructured text log (template mining) | file names |
| Shipping | `src_ship_sftp` | nightly `SHIP_YYYYMMDD_HHMM.csv` file drops | file name (batch), `po_num` |
| Shipping | `src_ship_log` | logfmt, one file per day | `shipment_no` (`SH-5521`), `po_num`, `manifest_id` |

Default run: 14 days from Wednesday 2026-09-23, 800 orders per weekday, weekends at half volume,
seed 1. Faults land on the spec's days: payments 503 spike day 6 (Monday), missing nightly file
day 9 (Thursday) preceded by `SFTP upload failed: Permission denied`, webstore outage day 10
(Friday) for 2 hours, `po_num` renamed to `po_number` on day 12, partial stall for
`warehouse_code=DC-03` on day 13 (Monday); warehouse clock runs 90 seconds fast throughout.
30% of purchase orders are keyed by clerks during business hours with 2% typos in `order_ref`.
